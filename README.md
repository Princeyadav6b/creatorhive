# CreatorHive

A creator gig marketplace: creators publish services, clients book them with a structured brief, and both sides track every request from pending to accepted or declined.

## Stack

- **TanStack Start** (React 19 + Vite 7, file-based routing, SSR)
- **TypeScript** (strict, `exactOptionalPropertyTypes`)
- **Tailwind CSS v4** design tokens in `src/styles.css` + **shadcn/ui**
- **Lovable Cloud** (Postgres, Auth, Row Level Security) — no external keys or `.env` setup needed
- **React Hook Form + Zod**, **TanStack Query**, **Lucide**, **Sonner**

## Routes

| Route | Access | Purpose |
| --- | --- | --- |
| `/` | public | Landing page: hero, featured gigs, categories, how it works, trust, CTA |
| `/marketplace` | public | Search, category / rate-type / price filters, sort, results count, load more |
| `/gigs/$id` | public | Gig details, similar gigs, booking modal + confirmation |
| `/gigs/new` | creator | Publish a gig |
| `/gigs/$id/edit` | creator (owner) | Edit a gig |
| `/creator/dashboard` | creator | Summary cards, booking requests with tabs + accept/decline, My Gigs management |
| `/my-bookings` | client | All requests sent, with status filter and search |
| `/bookings/$id` | participants | Full booking brief |
| `/sign-in`, `/sign-up` | public | Auth with role selection and demo logins |
| `/unauthorized` | public | Wrong-role page |
| any unknown path | public | Custom 404 |

## Data model

- `profiles` — `id`, `full_name`, `email`, `avatar_url`, timestamps
- `user_roles` — `user_id`, `role` (`creator` / `client`), unique per pair (roles are **never** stored on the profile)
- `gigs` — creator, title, category, rate, rate type, description, delivery days, cover image, `is_active`, timestamps
- `bookings` — auto reference number (`CH-YYYY-#####`), gig + creator + client snapshot, project title, requirements, dates, budget, contact email, reference link, status, timestamps

Timestamps and reference numbers are generated by the database, never the browser.

## Security

Row Level Security enforces every rule server-side:

- anyone can read **active** gigs; creators insert gigs only for themselves and update/delete only their own
- clients insert bookings only as themselves, always as `pending`, and never for their own gig
- clients read only their own bookings; creators read only bookings on their gigs
- only the booked creator can change a status, and only from `pending` to `accepted` / `declined`
- roles are checked through a `SECURITY DEFINER has_role()` function, so a browser cannot claim a role

## Local setup

```bash
bun install
bun run dev      # http://localhost:8080
bun run lint
bun run build
```

Backend credentials are injected automatically (`VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY`); no secret keys live in the codebase.

## Verified flows

Checked in a real browser against the running app: creator and client sign-in, publishing a gig, the new gig appearing in the marketplace, search and category filtering, booking a gig with confirmation + reference number, the booking appearing in My Bookings as pending, the correct creator seeing it in the dashboard, accepting and declining requests with status reflected on the client side, protected routes redirecting signed-out visitors to sign-in and wrong-role visitors to `/unauthorized`, data persisting across refresh, and mobile / tablet / desktop layouts — with no console errors.

## Known limitations

- No messaging, payments or file delivery — bookings stop at accepted/declined.
- Cover images are URLs; there is no image upload.
- A status change is final by design (no re-open), matching the spec.
